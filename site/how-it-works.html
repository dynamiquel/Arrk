Under the hood

One app. A lot of
quiet coordination.

Arrk is a single modular ASP.NET Core application, not a microservice per feature. It provisions Docker containers, configures each service through its REST API and keeps one coherent UI on top.

The shape of it

Everything starts at one front door.

The services still do the real work. Arrk owns the user experience, the configuration, the lifecycle rules and the glue between them. Their own UIs remain reachable when you need the deeper view.

  • One container with the Docker socket and three storage mounts
  • YAML config with hot-reload, validation and a schema-backed editor
  • Typed HTTP clients for every managed service
  • SQLite for Arrk, Hangfire and every managed service
  • Traefik for path-based routing and an optional Cloudflare tunnel

Concepts over implementations

You work with media. Arrk picks the tool.

Config and UI use user concepts — tv, music, jellyfin — never the names of the services underneath. One definition per concern, derived per service, keeps quality profiles, indexers and download clients from drifting apart.

Modules

The shell never knows which feature it is rendering.

A module contributes services, config sections, DI registrations, hosted services, jobs, HTTP endpoints and UI. The UI is composed from contracts for navigation, discovery tabs, named regions, head assets and dashboard tiles. A drop-in plugin uses the same seams as a built-in module.

Your pluginSame contracts, loaded from plugins/
MyModule.cs 
public sealed class MyModule : IArrkModule
{
    public string ModuleName => "MyPlugin";

    public IReadOnlyList<Service> GetServices() => [];

    public void ConfigureServices(
        IServiceCollection services,
        IConfiguration configuration)
    {
        services.AddSingleton<INavigationProvider, MyNavigation>();
        services.AddSingleton<ITileProvider, MyTiles>();
        services.AddSingleton<IHeadAssetProvider, MyHeadAssets>();
    }
}

A plugin is a normal class library.

Drop the DLL into <data>/plugins, restart Arrk, and it is loaded like a built-in module. It can add pages, navigation, dashboard tiles, jobs, endpoints and CSS.

  • Reference the abstraction assemblies, never a feature implementation
  • Use the shared --st-* theme tokens
  • A broken contribution is isolated by an error boundary

Honest status

What works, and what is still growing.

Arrk is early. The core loop is real and used daily, but this is not a finished commercial product. Here is the current shape of it, without the marketing gloss.

Working today
  • Modular UI and plugin loading, YAML validation, hot-reload and a visual editor
  • Docker provisioning with volumes, networks, GPU passthrough and VPN routing
  • Movies, shows, anime, native music, downloads, playback, subtitles and requests
  • Per-user watch history, watchlists, staleness and opt-in cleanup
  • Accounts, OIDC, Discord/MAL sign-in, notifications and optional AI
Still in progress
  • Automatic TLS certificate management
  • A dedicated simplified landing page for non-admin users
  • Notifications for every lifecycle event and completed grab
  • More AI actions, recommendations and import fallbacks
  • Cleaner module boundaries for a few concrete clients

Expect movement

Configuration keys, schema and UI can change between releases while the project is pre-1.0. Back up config, read release notes, and pin an image if you need stability.

Why this exists

Arrk is a personal project. It grew out of repeated frustration with the usual self-hosted media stack: services that each solve one thing well, but never quite feel like one product. It is shared so other people can use it, learn from it or make it better — not because it is finished. Expect changes, and please be kind in issues.

Boring architecture. Calm evenings.

That is the trade Arrk makes: one more container in exchange for one fewer pile of tabs.
